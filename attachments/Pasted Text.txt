KSB+ ENGINE — FROM-FIRST-PRINCIPLES IMPLEMENTATION MANDATE

Project: KSB+ Sovereign Binary Database Engine
Architecture: Native Binary Runtime + K Virtual Machine + Q Query Interface + Columnar Storage + Matrix Execution
Implementation Scope: Binary primitives through enterprise database execution
Implementation Language: K and Q exclusively
Design Principle: Build the engine from the binary representation upward. No existing database engine as a runtime dependency.

0. EXECUTIVE DIRECTIVE

Build KSB+ as an original, complete database engine inspired by the computational and time-series architecture of kdb+, implemented from first principles.

Do not begin with a SQL parser, an existing database, an ORM, or a high-level table abstraction.

Begin at the bottom of the stack: byte representation, integer arithmetic, memory layout, binary serialization, runtime values, vector execution, storage pages, transaction logging, and recovery. Build each higher layer on top of verified lower-layer primitives.

The implementation must use native K and Q. K is the foundational computation and data-processing layer; Q provides query evaluation and SQL compatibility. Where the chosen K/Q implementation environment cannot directly implement a required low-level primitive, explicitly document the limitation. Never pretend a high-level K expression provides direct control over physical memory, machine instructions, or operating-system facilities when it does not.

This is a new implementation. Do not copy proprietary Kx source code, reverse-engineer undocumented proprietary internals, or misrepresent architectural inspiration as compatibility.

Non-negotiable requirements:

- Build actual executable functionality at every layer.
- Implement binary formats and algorithms explicitly.
- No Python, Rust, C, C++, Java, or other language in the runtime.
- No external database delegation.
- No simulated persistence or mock transaction commits.
- No placeholder implementations reported as complete.
- No fabricated benchmark results.
- No premature claims of ACID compliance or production readiness.
- No stopping at a scaffold, README, architecture proposal, or collection of empty files.

1. LAYER ZERO — BINARY CONTRACT

Establish the physical binary contract before implementing the database.

Specify and implement:

1. Byte and bit representation.
2. Unsigned and signed integer encoding.
3. Fixed-width integer types.
4. Floating-point representation.
5. Boolean representation.
6. Endianness conversion.
7. Alignment and padding rules.
8. Variable-length integer encoding where useful.
9. Length-prefixed byte sequences.
10. String encoding and validation.
11. Null and missing-value encoding.
12. Checksums and integrity metadata.
13. Versioned binary structures.
14. Bounds checking and overflow detection.
15. Canonical serialization rules.

Every persisted structure must have a defined binary layout.

For every structure, document:

- Field offsets.
- Field widths.
- Alignment.
- Valid ranges.
- Null semantics.
- Version identifier.
- Integrity-check procedure.
- Compatibility and rejection behavior.

Implement executable encode/decode round-trip tests. Invalid, truncated, oversized, or corrupted inputs must fail deterministically without out-of-bounds access or silent data modification.

Do not assume the host's native representation is the persistent format.
